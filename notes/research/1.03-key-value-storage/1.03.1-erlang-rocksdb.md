

This is a strategic architectural evaluation and migration plan.

### Executive Summary

Transitioning from a custom Rust NIF to the **Erlang-RocksDb** (C++ NIF) library is a sound architectural decision. While both are technically NIFs (Native Implemented Functions) and thus execute outside the BEAM's memory management, the established Erlang-RocksDb ecosystem is highly optimized for the BEAM's scheduler constraints (specifically utilizing Dirty CPU and I/O schedulers) and removes the complexity of maintaining a separate Rust toolchain.

For a Knowledge Graph engine like **TripleStore**, where the workload is heavily dominated by random reads (Dictionary lookups) and range scans (Triple pattern matching), the maturity of the underlying C++ RocksDB wrapper and its ability to handle iterators efficiently via `fold` operations will provide more predictable performance than a bespoke Rust implementation.

### 1. Current State Analysis

Based on the repository structure and standard practices for Elixir NIFs:

*   **Storage Interface:** The engine currently relies on a `TripleStore.Native` module (or similar) that calls out to Rust code compiled via `rustler`.
*   **Data serialization:** The Rust NIF likely handles the serialization of Elixir terms (or binaries) into byte arrays for RocksDB.
*   **Bottleneck:** As noted, the Rust NIF creates a "hard" dependency on the NIF thread. If the Rust code performs long-running tasks (like iterating over a large dataset) without yielding, it halts the BEAM scheduler thread it is running on.
*   **Build Configuration:** `mix.exs` currently configures `rustler` compilers, and a `native/` directory contains the Rust source.

### 2. Target Solution: Erlang-RocksDb

**Repository:** [EnkiMultimedia/erlang-rocksdb](https://github.com/EnkiMultimedia/erlang-rocksdb)

*   **Nature:** This is a wrapper around the C++ RocksDB library.
*   **Scheduler Integration:** While it is a NIF, it adheres to standard BEAM practices. Long-running operations (like iterators) can be offloaded to Dirty IO schedulers, or better yet, the library provides `fold` functions that control the iteration loop in C/NIF land and release data back to Elixir in chunks, reducing context switching overhead.
*   **Column Families:** Essential for TripleStores. We must ensure the wrapper supports Column Families (CFs) to separate the **Node Dictionary** (String->ID mapping) from the **Triple Indices** (SPO, POS, OSP). Erlang-RocksDb supports this.

### 3. Gap Analysis & Requirements

To replace the Rust NIF, the following changes are required:

#### A. Dependency Management
*   **Remove:** `rustler` and any Rust build tools from `mix.exs`.
*   **Add:** `erlang-rocksdb` (usually referenced as `:rocksdb` in Hex, or pulled from the specific Git repo if not published on Hex).
*   **System Deps:** Ensure `librocksdb` (the C++ library) is present on the target system (either via package managers or compiled during the `erlang-rocksdb` build).

#### B. API Mapping (Elixir to NIF)
The Rust NIF exports functions that look like Elixir functions. These must be mapped to `:rocksdb` calls.

| Current Function (Rust NIF) | Target Function (`:rocksdb`) | Notes |
| :--- | :--- | :--- |
| `open_db(path, opts)` | `:rocksdb.open(path, opts)` | Must handle `create_if_missing`. |
| `close_db(db_ref)` | `:rocksdb.close(db_ref)` | Ensure this happens in a `on_exit` or `terminate` callback. |
| `get(db, key)` | `:rocksdb.get(db, key)` | Returns `:not_found` or `binary`. |
| `put(db, key, val)` | `:rocksdb.put(db, key, val)` | Direct mapping. |
| `delete(db, key)` | `:rocksdb.delete(db, key)` | Direct mapping. |
| `write_batch(db, batch)` | `:rocksdb.write(db, batch)` | Used for bulk loading triples. |
| `new_iterator(db)` | `:rocksdb.iterator(db)` | **Critical Change:** See Iteration Strategy below. |

#### C. Iteration Strategy (The "Semantic Web" Bottleneck)
In a Knowledge Graph, the most expensive operation is matching patterns like `?s :ex:knows ?o`. This requires iterating over all triples with predicate `:ex:knows`.

*   **Rust Approach:** Likely exposes a "next" function. This is terrible for BEAM performance because it crosses the BEAM-NIF boundary for *every single triple*.
*   **Erlang-RocksDb Approach:** Use `:rocksdb.fold`.
    *   `fold` allows the NIF to iterate rapidly in C++ land and accumulate results or stream them back in batches, drastically reducing the context switching overhead.
    *   *Requirement:* Replace manual "next/move" logic in Elixir with `:rocksdb.fold/4`.

#### D. Data Compatibility
*   **Serialization:** The Rust NIF might have used `rustler::Encoder` to turn Elixir terms into bytes. `erlang-rocksdb` only accepts binaries (`iodata`).
*   **Action:** The Elixir layer must now be responsible for binary serialization (e.g., `:erlang.term_to_binary/1` or a custom binary packing protocol for efficiency). Since we are building a high-performance engine, I recommend **custom binary packing** (e.g., packing integers into 64-bit little-endian binaries) rather than Erlang term formatting to save space and disk IO.

### 4. Comprehensive Migration Plan

#### Phase 1: Preparation & Dependency Removal
1.  **Branching:** Create a feature branch `feature/migrate-erlang-rocksdb`.
2.  **Clean `mix.exs`:**
    *   Remove `{:rustler, "~> x.x"}`.
    *   Remove `compilers: [:rustler] ++ Mix.compilers()`.
    *   Remove the `rustler` configuration block specifying the `native` crate.
3.  **Add New Dependency:**
    *   Add `{:rocksdb, "~> 1.8"}` (or the specific version from EnkiMultimedia) to `mix.exs`.
    *   Ensure the system has `librocksdb-dev` installed (document this in the README).
4.  **Code Cleanup:**
    *   Delete the `native/` directory and all `*.rs` source files.
    *   Identify the module that wraps the NIF calls (e.g., `TripleStore.Nif`).

#### Phase 2: Backend Adapter Implementation
1.  **Create `TripleStore.Backend.RocksDb`:**
    *   Create a new module or refactor the existing one to wrap the Erlang `:rocksdb` API.
    *   Implement `open/1`:
        ```elixir
        def open(path) do
          # Options must match the previous DB to read data!
          opts = [:create_if_missing, {:cache, &my_cache_handler/2}]
          case :rocksdb.open(String.to_charlist(path), opts) do
            {:ok, db} -> {:ok, db}
            {:error, _} = err -> err
          end
        end
        ```
2.  **Implement Basic Operations:**
    *   Map `get/3`, `put/4`, and `delete/3`. Ensure inputs are converted to binaries if they aren't already.

3.  **Implement Write Batches (Bulk Loading):**
    *   Replace the Rust batch logic with `:rocksdb.write/2`.
    *   Construct the batch using `:rocksdb.batch()`.
    *   **Optimization:** For SPARQL updates, grouping many triple operations into a single `:rocksdb.write` is critical for ACID compliance and performance.

#### Phase 3: High-Performance Iteration (Crucial Step)
1.  **Refactor Pattern Matching:**
    *   Locate code that iterates over ranges (e.g., `scan_spo(subject, ...)`).
    *   **Old Way:** `iter = open()`, `move(iter, key)`, `loop(next(iter))`.
    *   **New Way:** Use `:rocksdb.fold/4`.
    *   **Implementation Example:**
        ```elixir
        def fold_by_prefix(db_ref, prefix, acc, fun) do
          # Creates an iterator, seeks to prefix, and folds in C++ land
          :rocksdb.fold(db_ref, fun, acc, [{:iterator_options, {:seek, prefix}}])
        end
        ```
2.  **Index Scanning:**
    *   Since TripleStore uses indices (SPO, POS, OSP), `prefix` will be the binary representation of the bound parts of the triple.

#### Phase 4: Configuration & Tuning
1.  **Remove Rust Config:** Delete any Rust-specific config files (`.cargo/config`, `Cargo.toml`).
2.  **Tune RocksDB via Erlang:**
    *   Configure the block cache, bloom filters, and compression (Snappy or LZ4) inside the `open/2` options list.
    *   *Expert Tip:* Ensure `:total_order_seek` is set to `false` and use `:prefix_seek` if supported by the wrapper version, as this speeds up Triple queries significantly.

#### Phase 5: Data Migration Strategy (Zero-Downtime Goal)
*   **Format Compatibility:** Ideally, the Rust NIF wrote standard RocksDB key-value pairs. Since RocksDB is a storage engine, the file format on disk is compatible regardless of the client language (Rust vs C++), **provided** the serialization of keys/values is identical.
*   **Verification:**
    1.  If the Rust NIF used `:erlang.term_to_binary`, `erlang-rocksdb` will read it fine.
    2.  If the Rust NIF used a custom binary struct packing (e.g., `[u8; 8]`), verify that `erlang-rocksdb` reads these binaries exactly. (It will).
    3.  **If** the Rust NIF used a specific Compression Dictionary or custom Comparator, `erlang-rocksdb` must be initialized with the *exact same options* or it will fail to open the DB.

#### Phase 6: Testing & Benchmarking
1.  **Unit Tests:** Ensure all tests pass. specifically `TripleStore.RDF.Test` (or similar).
2.  **Performance Benchmark:**
    *   Run a complex SPARQL query (joins) against both the old (Rust) and new (Erlang) versions if possible.
    *   Measure `scheduler_usage`. The new version should show better distribution across schedulers or significantly reduced latency in `fold` operations.
3.  **Memory Monitor:** Check for leaks. NIF resource cleanup (`:rocksdb.close`) must be strict.

### 5. Technical Risks & Mitigation

| Risk | Mitigation |
| :--- | :--- |
| **Iterator Blocking** | Even with C++ NIF, iterators can block. Use `fold` where possible. If using raw iterators, ensure the logic inside the loop is minimal. |
| **Binary Encoding Mismatch** | If the Rust code manually packed integers (endianness), Elixir must match this. Use Elixir's `<<int::little-64>>` syntax to match Rust logic. |
| **Column Families** | If the existing DB uses Column Families, `:rocksdb.open` *must* provide a list of existing column families with their handles. Failing to list them will result in a "Status::InvalidArgument" error. |
| **Dirty Scheduler Limits** | If the DB is massive, reads/writes might hit Dirty Scheduler limits. Monitor VM logs for "scheduler busy". |

### Conclusion

By moving to `erlang-rocksdb`, we are trading a **custom, unmaintainable NIF bridge** for a **standard, community-optimized driver**. The primary engineering effort lies not in the API translation (which is straightforward), but in ensuring the **Iteration Logic** (critical for SPARQL performance) is refactored to use `:rocksdb.fold` rather than manual iterator traversal, and ensuring the **Column Family** configuration perfectly matches the existing database state.
